01 · 가장 먼저

Git과 GitHub는 같은 것이 아닙니다

📚 Git

내 PC의 버전관리

파일 변경을 기록하고 Branch를 관리합니다. 아래 명령은 한꺼번에 실행하는 예제가 아니라 각각 서로 다른 역할을 가진 명령입니다.

예: Git 저장소 시작
git init
→ “이 폴더에서 Git 관리를 시작해 줘.”
예: 파일을 다음 저장 대상으로 선택
git add 파일명
→ “이 파일을 다음 Commit에 포함해 줘.”

☁️ GitHub

인터넷의 저장·협업 공간

Local Git의 Commit과 Branch를 원격 Repository에 공유합니다.

예: GitHub로 보내기
git push
→ “Local에 저장된 Commit을 GitHub로 보내 줘.”
예: GitHub 내용 가져오기
git pull
→ “GitHub의 최신 내용을 내 PC로 가져와 줘.”
⭐ 핵심: 이 교재의 모든 명령은 한 줄 입력 → Enter → 결과 확인 → 다음 명령 순서로 실행합니다. Commit했다고 GitHub에 올라간 것도 아닙니다.

04 · 가장 많이 헷갈린 부분 #1

Branch를 만들면 GitHub에도 바로 생긴다?

Git Bash
$ git switch -c second

$ git branch

⭐ git switch -c second는 Local Branch만 만듭니다. GitHub에 보이게 하려면 git push -u origin second.
05 · 파일을 안 고쳤는데?

새 Branch를 Push하려면 add/commit이 꼭 필요한가?

파일 변경 없음

STEP 1 · Local Branch 생성
git switch -c second
Enter → second로 이동했는지 확인
STEP 2 · GitHub에 Branch 게시
git push -u origin second
Enter → GitHub에 second가 생성됨

기존 Commit을 가리키는 새 Branch를 Remote에 게시할 수 있습니다.

파일을 수정함

STEP 1
git add .
STEP 2
git commit -m "수정"
STEP 3
git push

새 변경을 Commit한 뒤 Remote에 전송합니다.

정답: git push -u origin second. 새 add/commit은 필요하지 않습니다.

08 · 목적지 변경

GitHub Repository 정확한 주소 확인하기

Repository 주소는 직접 타이핑하지 말고, GitHub 화면에서 복사해서 사용합니다. 이 습관 하나로 Repository not found 오류를 크게 줄일 수 있습니다.

☁️ GitHub
Repository 접속
→
<> Code
버튼 클릭
→
HTTPS
주소 복사
→
💻 VS Code
remote와 비교

STEP 1 · GitHub에서 복사

GitHub에서 올릴 Repository로 들어갑니다.
파일 목록 위쪽의 <> Code 버튼을 클릭합니다.
HTTPS 탭을 선택하고 복사 아이콘을 누릅니다.
https://github.com/jasonkey72-afk/git_study.git
→ 이런 형태의 주소가 Git 연결용 Repository 주소입니다.

STEP 2 · VS Code에서 현재 주소 확인

한 줄 입력 후 Enter
git remote -v
→ 현재 Local 프로젝트가 어느 GitHub Repository로 연결되어 있는지 확인합니다.
주소가 다르면 한 줄 입력 후 Enter
git remote set-url origin <복사한 HTTPS 주소>
→ origin의 목적지를 정확한 Repository 주소로 바꿉니다.
초보자 원칙: Repository 주소는 기억해서 입력하지 않습니다. GitHub의 <> Code → HTTPS → 복사로 가져옵니다.
09 · 기존 파일 하나만 올리기

Repository 주소를 잘못 연결했다면?

GitHub Repository → <> Code → HTTPS에서 URL 복사
git remote -v
현재 목적지 확인
git remote set-url origin https://github.com/OWNER/정확한이름.git
목적지 변경
git remote -v
반드시 다시 확인
추천 습관: Push 직전 git remote -v + git branch. “어디로?”와 “어느 Branch?”를 동시에 확인합니다.
10 · 오류 실전 #1

git_study.html만 GitHub에 올린다면

아래는 6개 명령을 한 번에 실행하는 것이 아닙니다. 반드시 STEP별로 한 줄씩 실행하고 결과를 확인합니다.

STEP 1 · 폴더 이동
cd /c/Python/company/git_test
→ git_study.html이 있는 폴더로 이동
STEP 2 · Git 시작 (처음 한 번만)
git init
→ 이미 Git 저장소라면 다시 할 필요 없음
STEP 3 · 이 파일만 선택
git add git_study.html
→ 다른 파일이 아니라 git_study.html만 다음 Commit 대상으로 선택
STEP 4 · Local에 저장
git commit -m "git_study 최초 등록"
→ 내 PC의 Git에 하나의 버전으로 저장
STEP 5 · GitHub 목적지 연결 (처음 한 번만)
git remote add origin <GitHub HTTPS URL>
→ GitHub Repository를 만드는 명령이 아니라 주소를 등록하는 명령
STEP 6 · GitHub로 전송
git push -u origin main
→ Local main의 Commit을 GitHub로 보냄
이미 Commit되어 있고 working tree clean이라면 STEP 3·4를 다시 하지 않습니다. 목적지 연결도 이미 되어 있다면 STEP 5를 다시 하지 않습니다.

12 · 오류 실전 #3

src refspec ... does not match any

원인 A

Push하려는 Branch가 Local에 없음.

먼저 확인

→ feature/signup이 없다면 다음 명령
git switch -c feature/signup

최초 저장소인데 아직 Commit 자체가 없음.

Enter → 그 다음

13 · 오류 실전 #4

Repository not found

Local origin
→
주소 오타 / Repo 없음
또는 접근권한 문제
git remote -v

GitHub에서 실제 Repository가 존재하는지, <> Code → HTTPS 주소와 일치하는지 확인합니다.

git remote set-url origin <복사한 정확한 URL>
중요: git remote add origin ...은 GitHub Repository를 “생성”하지 않습니다. Local에 목적지 주소를 등록할 뿐입니다.
14 · VS Code 실전 루틴

Updates were rejected because the remote contains work...

LOCAL

git_study.html Commit

●

GITHUB

README 등 별도 Commit

●
둘이 서로 다른 시작 이력을 가지면 Push가 거절될 수 있습니다. 기존 Local 프로젝트를 처음 올릴 때 GitHub의 새 Repository를 README / License / .gitignore 없이 빈 저장소로 만들면 가장 단순합니다.
STEP 1 · GitHub 이력을 Local로 가져와 합치기
git pull origin main --allow-unrelated-histories
→ Enter 후 결과를 확인합니다. 충돌이 있으면 해결이 먼저입니다.
STEP 2 · 합치기가 정상 완료된 뒤에만 Push
git push -u origin main
→ STEP 1이 성공한 것을 확인한 후 별도로 실행합니다.

⚠️ 초보 실습에서는 무작정 git push --force를 사용하지 않습니다.

16 · 한 장 요약

Git 초보자의 생존 공식

① Local ≠ GitHub

Branch/Commit은 먼저 내 PC에 존재할 수 있다.

② Commit ≠ Push

Commit은 Local 저장, Push는 Remote 전달.

③ origin = 목적지

git remote -v로 Repository 확인.

④ * = 현재 Branch

git branch로 작업 위치 확인.

⑤ U/M/A는 상태표시등

파일이 어느 단계인지 알려준다.

⑥ 막히면 status

git status가 가장 먼저 볼 진단 화면.

외우지 마세요. “Local인가? Remote인가? 파일인가? Commit인가? Branch인가?”만 구분하면 대부분의 Git 오류가 읽히기 시작합니다.
